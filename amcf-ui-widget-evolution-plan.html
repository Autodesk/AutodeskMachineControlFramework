AMCF UI Evolution Plan

Goal: define a cohesive next-generation widget architecture for robust HMI design, with a dedicated and expandable form module and clear compatibility path from the current AMCF schema.

1. Target Architecture Principles

Schema-First Widgets

Every widget is declared by typed JSON schema with stable contracts and backward-compatible defaults.

Composable Layout

Widgets nest cleanly under grid, tabs, content (card variants), dialogs, and future split panes without custom one-off logic.

Unified Event Model

All widgets emit events via /api/event with source widget UUID and value payload. Server-side validation uses /api/validate.

Responsive by Default

Desktop/wall-panel/mobile behavior is explicit in widget properties. Form builder preview mode is a Phase 3 target.

The component now fills height: 100% inside Grid cells. Card styles render title / subtitle using Vuetify v-card-title / v-card-subtitle for professional appearance.

6. App Layout Fixes (Feb 2026)

Fixed The root application layout was refactored from JavaScript pixel calculation to CSS flex for reliable full-height behaviour:

  • Content card expanded from width: 90% (centred) to width: 100%.
  • Height is now managed via .v-main__wrap { display:flex; flex-direction:column; height:100% } rather than window.innerHeight arithmetic.
  • Page v-container replaced with a plain div to eliminate Vuetify's breakpoint max-width cap.
  • margin: auto removed from card style so it no longer forces centering.

7. Bug Fixes Applied (Feb 2026)

LayerView / GLScene

  • Fixed module.uuid scoping error in created() hooks of both AMCModule_LayerView.vue and AMCModule_GLScene.vue.
  • Fixed LayerViewerInstance is now always initialised in created(), preventing null-dereference during render when the WebGL instance is retrieved from cache.
  • Fixed Platform item is now synthesised from v2 module attributes (platformuuid) in _normalizeV2ToLegacy(), so the build plate renders correctly in v2 mode.
  • Fixed baseimageresource attribute registered as the resource UUID (not the filename) so /image/{uuid} resolves correctly.
  • Fixed layercount uses Assert.OptionalIntegerValue to default to 0 when absent from v2 attributes.

BuildList Thumbnails

  • Fixed defaultthumbnail UUID is now exposed from C++ via v2 attributes so the JS module can use it as a fallback when job.thumbnail is absent from /api/build responses, preventing thumbnails from vanishing on load.

10. Migration and Delivery Plan

Phase 1: Stabilize Existing Widgets — Complete

  • Done: migrate client traffic from /ui/* to dedicated /api/* handlers and unregister CAPIHandler_UI.
  • Done: promote all 12 former content-item types to first-class modules in backend (CUIModule_ContentLeaf) and frontend (AMCModule_Factory.vue component map).
  • Done: implement v2 frontend state via /api/frontend with frontendWriteItemToJSON/frontendWriteModuleStatusToJSON; mark /api/state as deprecated.
  • Done: add v2 format normalisation (_normalizeV2ToLegacy()) and ContentLeaf unwrapping in client so both legacy and v2 payloads render correctly.
  • Done: implement ModuleFactory pattern in Vue 2 client, replacing ContentLeaf abstraction with direct component resolution by module.type.
  • Done: v2 widget support for chart, image, form, parameterlist, configurationlist, logs, graphic, glscene, layerview, and custom modules.
  • Done: standardised visible, enabledWhen, readonlyWhen cross-cutting properties via CUIExpression dynamic expressions on all v2 modules.
  • Done: runtime schema validation added (AMCModuleSchema.js, validateModuleJSON) to catch malformed module payloads before rendering.
  • Done: fix known form/list issues — string validation, alert row mapping, configuration action schema usage.
  • Future: shared tableplus base — migrate parameterlist, alertlist, buildlist, executionlist, configurationlist. (Phase 3)

Phase 2: Form as First-Class Module — Complete

  • Done: form promoted from content item to module-level citizen with its own layout engine and section model.
  • Done: new field types — number, slider, datetime, multiselect, calculated.
  • Done: section containers — collapsible, defaultopen, icon, description.
  • Done: validation engine — field-level in AMCFormField.vue checkRules(); cross-field and form-level via /api/validate (CAPIHandler_Validate).
  • Done: form action bar with submitevent, cancelevent, validateevent, dirty-state tracking, optimistic/pessimistic submit policies.
  • Done: reusable AMCFormField.vue component encapsulates rendering, local rules, and server error display for all field types.
  • Done: AMCApplication.js validateFormValues() method calls /api/validate and resolves to { valid, errors }.
  • Done: content module card widget upgrade — cardstyle, spacing, elevation, cardcolor attributes; full-height layout.
  • Done: App.vue full-width/full-height layout refactor (CSS flex replacing JS pixel calculation).

11. Technical Decisions Status

DecisionStatusImpact
State transport model Done: v2 frontend schema/event model is primary via /api/frontend; dedicated /api/* handlers replace /ui/*; /api/state deprecated. Client supports both v2 and legacy via _normalizeV2ToLegacy(). Cleaner data flow, fewer race conditions, and a path to remove legacy compatibility code.
Module factory model Done: Vue 2 client uses AMCModule_Factory.vue component map (20+ types); C++ backend uses CUIModuleFactory::createModule() with CUIModule_ContentLeaf wrapper for leaf types. Uniform module instantiation, simpler rendering pipeline, no container dependency for leaf types.
Server-side validation Done: /api/validate endpoint (CAPIHandler_Validate) accepts eventname + formvalues JSON and parses VALIDATIONERROR:{...} exceptions into per-field error maps. Cross-field and server-constraint validation without custom API endpoints per form.
Schema governance Define JSON schema versions and compatibility policy (schemaVersion). Safe rollout of new widgets and properties.
Design tokens Current: Vuetify light theme colors applied from /api/config. content module has cardstyle/cardcolor/elevation/spacing. Next: centralised token map (spacing, typography, colors, state tones). Consistent HMI look and fast theme changes.
Event naming convention Current: ad-hoc names (changeevent, submitevent, cancelevent, validateevent) via /api/event. Phase 3: namespace all events (module.action.intent). Easier backend contract maintenance and tracing.
Builder storage Store generated schemas as versioned server artifacts with diff/audit. Traceable HMI evolution and rollback safety.

12. Content Module Deprecation Plan

Note: The content module has been upgraded (card styles, spacing, height:100%) and is no longer a simple deprecation target. It now serves as a useful layout/card container. The long-term plan shifts toward making child modules first-class citizens while content becomes a composable panel wrapper.

Revised goal: Keep content as the canonical card/panel container. Deprecate only the use of content as a data widget host (i.e., wrapping individual data widgets that could stand alone). Pages should eventually contain grid + content + direct first-class modules, not chains of nested content > content > item.

Current state (Feb 2026): Steps 1–5 are complete. All 12 leaf types have backend and frontend first-class support. Legacy <content> XML is still used in all Example configs.

14. Success Criteria

  • Done: v2 frontend state model is operational via /api/frontend. Legacy path removed.
  • Done: Full-featured form screens can be built in XML/schema — 9 field types, sections, validation, action bar.
  • Done: Server-side cross-field validation available via /api/validate with per-field error maps.
  • Done: Content module supports card-style presentation with configurable elevation, spacing, and background.
  • Future: One responsive form definition supports desktop + panel + tablet layouts (Phase 3 — form builder).
  • Future: Widget event contracts are typed and documented; no ad-hoc payload guessing (Phase 3 — event namespace).
  • Future: At least 80% of current custom one-off table/list logic replaced by shared base modules (Phase 3 — tableplus).
  • Future: Operator-critical actions support role checks + confirmation + audit context (Phase 3 — policy packs).

Result: cohesive, scalable HMI architecture with lower maintenance cost and faster screen delivery.

This plan is designed to be implemented incrementally while keeping current AMCF page/module JSON definitions functional. Last updated: Feb 2026.
